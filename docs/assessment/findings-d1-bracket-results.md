## Findings

**Required:** ~~`review_match_result` never checks `m.status`~~ — **RESOLVED (202610181200):** raises "already has a result" unless `p_action='reject'`; `declare_forfeit` now auto-rejects open submissions; UI hides approve/override on completed matches (`ResultSection.tsx`). Original finding: (`202610171500_match_results.sql:368-375` locks the rows but only verifies `s.status`; the apply-update at :409-414 runs regardless of match state). Concrete scenario: captain submits "A wins 2-1"; staff instead calls `declare_forfeit` for B (which never checks for open submissions, `202610171400:165-203`) → match completed, `is_forfeit=true`, B advanced into the next match. The pending submission is still listed as `result_pending`, and another organizer pressing **Approve** on `/matches/[id]` rewrites the match to score 2-1 winner=A, silently clears `is_forfeit` via `match_checkin_rules` (`171400:146-151`), and — if the next match is still `scheduled` — swaps B→A in the downstream slot with no re-confirmation. The UI keeps showing the full staff-review panel whenever an `open` submission exists, even on a completed/forfeited match (`ResultSection.tsx:169-251` renders review controls under `{open && …}` + `{isStaff && …}` with no `match.status` guard). Symmetric gap: `declare_forfeit` doesn't reject or close open submissions, so the stale row lingers forever unless reviewed.

**Required:** ~~Bracket regeneration silently deletes submitted-but-unreviewed results.~~ — **RESOLVED (202610181200):** `generate_bracket` raises when any open submission exists in the tournament. Original finding: The regen guard (`202610161800:42-49`) only counts matches that are `live`/`completed` with both teams. But `submit_match_result` allows submissions on a `scheduled` match whose `scheduled_at` has passed (`202610171500:238-240`), and `check_in_match` likewise. So: a scheduled match past its time with a `confirmed` submission and both teams checked in → `generate_bracket` succeeds → `delete from matches` (:72) cascades away the submission, check-ins and predictions, nulls `streams.match_id`/`feedback.match_id`, and the proof file is orphaned in storage (no delete policy by design). Prediction loss is documented; losing a submitted-but-unreviewed result and its dispute history is not documented anywhere.

**Required:** ~~No integrity check on `next_match_id`~~ — **RESOLVED (202610181200):** `check_match` enforces same-tournament/not-self/target-scheduled when the value changes; verified live (self-feed rejected). Original finding: Admin/staff can update every column on `matches` (`202610161700:54-58`) and `check_match` doesn't validate `next_match_id` — staff can point a match at a match in a **different tournament** (the winner is then written into the wrong bracket by the advance trigger, since it only reads the row's own `match_number` parity, :143-147), at an already-live/completed match (the match then can never be completed), or at the match itself (self-feed → the advance trigger reads its own now-completed status and raises "next match already started" → permanently stuck). Related: the advance trigger is INSERT/UPDATE-only (:152-154), so **deleting** a completed match leaves the stale advanced team sitting in the next match's slot.

**Nit:** The "results lock once the next match starts" only locks winner changes. Score-only edits on a completed match still succeed after the next match went live (early return when `winner_team_id` unchanged, `202610161700:126-128`); `check_match` keeps winner>higher-score consistency, so it's a soft lock — and staff can always flip the next match back to `scheduled`, edit, re-`live`. Probably intended as an escape hatch, but the doc sentence overstates it.

**Nit:** `matches_notify` is AFTER UPDATE only (`202610171200:208-210`) — a match inserted with `scheduled_at` already set never sends `match_scheduled`. Similarly `log_match`'s INSERT branch treats any inserted match with `next_match_id is null` as "the final" and writes a `bracket.generated` activity entry (`202610171100:202-211`, latest `202610171400:237-247`) — a hand-inserted match produces a bogus bracket-generated log line.

**Nit (fixed elsewhere):** the check-in-vs-reschedule micro-race noted in findings-d2 is closed — `check_in_match` now locks the match row `for update` (202610181200).

**Nit:** `check_in_match` doesn't require both teams to be known (`202610171400:94-119`). If staff sets a time on a match with a TBD slot, the known team's captain can check in while the TBD slot can never check in; `get_needs_attention` inner-joins both teams (`202610171500:473-474`) so such a match never surfaces as `no_checkin` — inconsistent surfacing of the same state.

**Nit:** Scores can be pre-entered on a `scheduled` match — `check_match` allows scores without winner/status and the UI only disables score inputs when teams are unknown (`matches/page.tsx:271-281`). Harmless but a weird persisted state.

**FYI:** Concurrent staff edits on the same match are last-writer-wins: `MatchCard.handleSave` writes all editable fields in one update (`matches/page.tsx:225-235`), so two organizers editing concurrently overwrite each other's unchanged-looking fields; the `key={match.updated_at}` remount (:152) only protects after a save+reload.

**FYI:** `mark_predictions` returns before `check_prediction`'s `new.updated_at := now()` (`202610181100:87` vs :95), so `predictions.updated_at` isn't bumped when `is_correct` is marked — cosmetic.

**FYI:** Verified-correct behaviors worth noting explicitly: winner change mid-bracket (A→B override while the next match is still scheduled) correctly rewrites the downstream slot rather than leaving a stale team (:143-147); clearing the winner empties the slot; downstream `live`/`completed` blocks all of that; predictions re-mark on winner changes and reset on clear (:156-161); the single-open-submission race is covered twice (serialized `for update` on the match row + `match_results_one_open` partial unique index, with 23505 mapped in `utils/errors.ts:31`); a confirmed submission cannot be re-disputed (`respond` requires `status='pending'`, :310), so "confirmed-then-disputed" chains can't occur.
