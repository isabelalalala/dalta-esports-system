# Findings — C: Database integrity and RLS

## Verdict

RLS coverage is complete — every public table enables RLS and every documented matrix is faithfully implemented — but several documented invariants are only enforced at function/policy level and can be bypassed: `tournaments.status` is nullable, `tournaments.updated_at` is never maintained, `topics ≤3` has no CHECK, NULL boolean arguments bypass "reason required" rules in two functions, and a teammate's email can leak to a captain via an exception message.

## Checked

- **RLS enablement** — all 21 live `create table` targets plus `profiles`/`tournaments`/`tournament_registrations` (created outside migrations) have `enable row level security`; `team_join_codes` was dropped in `202610161400`; `storage.objects` policies exist for both buckets (`match-proofs`, `site-images`).
- **Policy fidelity** — compared every policy against CLAUDE.md's matrix for: profiles, games, tournaments, player_game_profiles, teams, team_members, team_invites, tournament_registrations, matches, match_checkins, match_result_submissions, predictions, announcements, streams, stream_views, feedback, analytics_reports, activity_logs, notifications, the 8 site-content tables (`202610171600`), and gemini_calls. All read/write matrices match the doc except as noted below.
- **SECURITY DEFINER functions** — all ~60 definer functions set `search_path = ''`; internal helpers are revoked from `public/anon/authenticated` (`log_activity`, `notify_users`, `team_member_ids`, `staff_ids`, `match_result_label`, `unverified_team_members`, `log_name`, `feedback_server_key_ok`, `checkin_window`, `send_checkin_open_notifications`, `purge_*`); app-facing functions have the documented role/ownership checks (`get_my_role`/`current_user_role`, `handle_new_user`, `protect_profile_role`, `give_privacy_consent`, `review_student_verification`, `check_in_match`, `submit_match_result`, `respond_to_match_result`, `review_match_result`, `declare_forfeit`, `generate_bracket`, `respond_to_team_invite`, `transfer_team_captaincy`, `admin_delete_user`, `delete_own_account`, `save_feedback_sentiment`, `mark_feedback_pending`, `claim_gemini_call`, `get_public_tournament`, `get_public_calendar`, `get_prediction_split`, `get_prediction_leaderboard`, `get_team_invites`, `get_my_team_invites`, `get_needs_attention`, `report_*`, `log_export`, `search_players`, `get_team_roster`, `activity_log_actors`).
- **Constraints** — verified roles enum, all status enums, rating 1-5, sentiment_score -1..1, scores ≥0, `score_a <> score_b`, facebook https URL regex, `registration_deadline ≤ start_date` / `end_date ≥ start_date` (NOT VALID, as documented), `checkin_window_minutes` 0-240, comment 3-1000, all documented unique indexes (`feedback_one_per_target` NULLS NOT DISTINCT, `team_invites_one_pending`, `match_results_one_open`, `profiles_student_id_unique` lower(), `official_team_players_one_captain`), generated `is_verified`.
- **Triggers** — every redefined function's latest version wins (no stale duplicates; superseded policies/triggers/functions are explicitly dropped: `"Captain can add players"`, `team_members_notify`, `notify_team_member()`, `join_team()`, `team_join_codes`, all policy-replacement loops). Transaction-scoped flags (`app.giving_privacy_consent`, `app.reviewing_student`, `app.answering_invite`, `app.transferring_captain`, `app.declaring_forfeit`, `app.marking_predictions`) are set with `is_local=true` and reset, so they can't leak past the transaction.
- **FK graph** — spot-checked only for doc-violations; all `on delete` behaviors match CLAUDE.md.
- **Indexes** — hot paths exist (matches.tournament_id via `unique(tournament_id,round,match_number)`, match_checkins via `unique(match_id,team_id)`, `predictions_match_idx`, `feedback_tournament_idx`/`feedback_match_idx`, `notifications_user_idx`, `activity_logs_*`, stream_views unique covering stream_id).

## Findings

**Required:**

1. **`tournaments.status` is nullable** — `202610161600_tournament_details.sql:65-70` adds `check (status in ('upcoming','cancelled'))` and `set default 'upcoming'` but never `set not null` (unlike `tournament_registrations.status` at `202610161500_registration_approval.sql:35`, which does). CHECK constraints pass on NULL, so admin/staff can store `status = null`, contradicting "only `upcoming` or `cancelled` is stored". Fix: `alter column status set not null`.

2. **`tournaments.updated_at` is never maintained** — CLAUDE.md lists `updated_at` on tournaments, but no migration adds a touch trigger for it, and the edit page updates without it (`app/tournaments/[id]/edit/page.tsx:89-102`). `changed_columns` explicitly ignores `updated_at` (`202610171100_activity_log.sql:88`), so the design clearly expects it to always bump; it never does.

3. **`review_student_verification(user, NULL, note)` bypasses the required reason** — `202610171000_student_verification.sql:148-149`: `if not p_approve and length(trim(coalesce(p_note,''))) = 0` — when `p_approve` is NULL, `not p_approve` is NULL so the guard is skipped, then line 156 `case when p_approve then 'verified' else 'rejected' end` treats NULL as reject. A null `p_approve` rejects (and can revoke a verified player) with no note, violating "rejecting or revoking needs a reason". Fix: `coalesce(p_approve,false)` or `p_approve is not true`.

4. **`respond_to_match_result(sub, NULL, reason)` disputes without a reason** — same pattern at `202610171500_match_results.sql:313-314`: `if not p_confirm and length(trim(coalesce(p_reason,''))) = 0` is skipped for NULL `p_confirm`, and lines 318-319 then set `status = 'disputed'` with `dispute_reason = left(trim(NULL),500) = null`. Violates "dispute needs a reason".

5. **`feedback.topics` has no DB-level constraint** — column is just `topics text[] not null default '{}'` (`202610162200_feedback.sql:21`). The documented "max 3 short lowercase labels" is only enforced inside `save_feedback_sentiment()` (`202610181000_feedback_protection.sql:243-249`). The admin UPDATE policy (`202610162300_admin_reports.sql:25-29`) plus `protect_feedback` (`202610181000_feedback_protection.sql:108-132`, which guards only rating/comment/created_at/links) lets an admin store arbitrary topic arrays and also write `analysis_*`, `classified_at`, and `target_removed` directly — wider than "write ONLY the sentiment fields". Fix: `check (cardinality(topics) <= 3)` (lowercase enforced by the writer) and optionally guard `target_removed`/`analysis_*` in the trigger.

6. **`unverified_team_members()` leaks member emails to captains** — `202610171000_student_verification.sql:184` uses `coalesce(p.full_name, p.email)`, so the registration/approval error ("Not verified yet: %", lines 260, 335) surfaces a teammate's email to the registering captain when the member has no name. This contradicts the design elsewhere (roster deliberately dropped email at `202610161400:183-211`; "never emails" in CLAUDE.md). The function can't be called directly (revoked, line 190), but its return value reaches the caller via the exception text.

7. **The captain of a team needs no game profile for the team's game** — `check_team_member()` only applies the game-profile check to `role = 'player'` rows (`202610171000_student_verification.sql:376-389`); the captain row added by `setup_new_team()` skips it, and the `teams` insert policy (`202610151200_team_registration.sql:122-125`) only requires `role = 'player'`. Consequence: a player can create a Tekken 8 team with no Tekken profile and register it solo for a Tekken tournament (min_players = 1), producing a roster with NULL IGN. CLAUDE.md's rule "trigger checks game profile" is described for invites; the same check presumably should apply to the captain's member row.

**Nit:**

8. `teams` captain update is wider than "name and description": policy `202610161400_team_captain_management.sql:17-21` + `protect_team_fields` (`202610171300_team_invites.sql:231-245`) guard only `game_id`/`captain_id`; `created_at` is silently writable by the captain (`id` too, but FKs reject that).
9. `check_prediction` doesn't restore `created_at`/`id` on UPDATE and doesn't fix `created_at` on INSERT (`202610181100_predictions.sql:90-98`): users can back-date picks, skewing `report_engagement` which filters on `pd.created_at` Manila date (same file, lines 309-310). Add `new.created_at := old.created_at` / `new.created_at := now()`.
10. `protect_profile_role` guards role/id/email/consent but not `created_at` (`202610170900_privacy_consent.sql:52-87`), so a user can rewrite their own join date, which feeds `report_activity`'s `signups_by_month`.
11. `review_match_result` treats `p_action = NULL` as 'override' rather than rejecting it — `202610171500_match_results.sql:364-365`: `p_action not in ('approve','override','reject')` is NULL → guard skipped → falls into the else/override branch (lines 396-405). Staff-only, but the silent fallback is fragile.
12. `site_content` has insert/update policies but no delete policy (`202610171600_public_website.sql:39-48`) — consistent with fixed keys, but undocumented; also `updated_by` is forgeable by an admin (no `= auth.uid()` check, unlike announcements line `202610162000:35`) and `updated_at` relies on the app (SiteTextEditor.tsx:59).
13. Site-content `link` CHECKs allow protocol-relative URLs: `link is null or link like '/%' or link like 'https://%'` (`202610171600:57,69,81`) — `'//evil.com'` matches `'/%'`. The notifications CHECK explicitly adds `and link not like '//%'` (`202610171200_notifications.sql:29`); these tables lack that. Admin-only input, low impact.
14. `teams` `unique (name, game_id)` (`202610151200:112`) is case-sensitive — "Team A" and "team a" coexist per game, unlike `profiles_student_id_unique` which deliberately uses `lower()` (`202610171000:37-39`). *(Independently found by D2 — see findings-d2.)*
15. `check_prediction` raises "Organizers can't make picks" on DELETE too (`202610181100_predictions.sql:100-116`), so a player promoted to staff/admin can never delete pre-promotion picks (they still get marked correctly — harmless residue).
16. `team_members` delete policy lets admin/staff remove the `role='captain'` member row (`202610151200:175-190`), leaving `teams.captain_id` pointing at a user who is no longer a member — captain functions still work but the roster loses its captain. *(Independently found by D2.)*
17. Missing indexes on real query paths: `team_members.user_id` (unique is `(team_id, user_id)` at `202610151200:163`; `tm.user_id = auth.uid()` lookups in `check_prediction`, `team_member_ids`, "my teams" pages seq-scan), `tournament_registrations.team_id` (unique `(tournament_id, team_id)` at `202610151200:356-359`; roster-lock check filters `r.team_id`), `feedback.user_id` ("Users read their own feedback" has only `feedback_tournament_idx`/`feedback_match_idx`), `gemini_calls.user_id` (per-user rate-limit lookup; tiny table, lowest priority).
18. `player_game_profiles` update/delete policies (`202610161300:34-43`) don't require `role = 'player'` like the insert does — a demoted player keeps full write access to orphaned game profiles.
19. `protect_team_invite` doesn't guard `id` (and lets `responded_at` be submitted, though it's overwritten) — `202610171300:152-166`; cosmetic since nothing references `team_invites.id`.
20. `streams` update has no `created_by`/`created_at` preservation (unlike `touch_announcement`) — `check_stream` (`202610162100_live_streaming.sql:56-72`) only validates the match link and bumps `updated_at`; admin/staff can rewrite `created_by`.
21. `give_privacy_consent` accepts any non-empty version string (`202610170900_privacy_consent.sql:102-111`); harmless because the consent gate compares against `PRIVACY_NOTICE_VERSION`, but no validation that the version is the real current one. *(Also in findings-l.)*
22. `respond_to_team_invite(id, NULL)` silently declines — `case when p_accept then 'accepted' else 'declined'` (`202610171300:218-220`); harmless but same NULL-boolean pattern as findings 3-4.

**FYI:**

- `advance_match_winner` clears the next match's team slot on INSERT when `new.winner_team_id` is NULL and `next_match_id` is set (`202610161700_matches.sql:143-147`) — a manual re-insert of a feeder match could wipe an already-filled slot; admin-only path.
- A captain can delete a team holding an **approved** registration as long as no bracket exists: `prevent_team_delete_in_bracket` only checks `matches` (`202610161700:160-177`), and `tournament_registrations.team_id` is `on delete cascade` (`202610151200:349-350`), so the registration silently disappears instead of becoming `cancelled` — a deliberate-looking design ("deleting the whole team is not blocked", `202610171300:292`), but it bypasses "captain can cancel or delete only while pending".
- `protect_feedback` allows clearing `user_id`/`tournament_id`/`match_id` to NULL for *any* update that reaches it, not just FK `set null` cascades — an admin can anonymize a feedback row manually (`202610181000:116-128`), which then also sets `target_removed`.
- `claim_gemini_call` limits count rows, not `sum(items)` (`202610181000:198-211`); verified correct because the server claims once per Gemini request (`utils/feedback-analysis.ts:40-43`) and stores `items` only informatively.
- `advance_match_winner`'s `FOR UPDATE` + `next_status <> 'scheduled'` refusal also fires on INSERT with a dangling `next_match_id`; FK prevents that in practice.
- `get_prediction_leaderboard` returns no row for a caller with zero picks despite "top 20 + your row" (`202610181100:236-237`) — caller simply isn't in `scores`; cosmetic.

## Unverifiable locally

- Whether all 25 migrations were actually applied, in filename order, on the live DB (later definitions assume it; e.g. `protect_feedback` latest is `202610181000`, `notifications_type_check` latest is `202610171500`).
- Whether the dynamic cleanups caught every pre-migration object: policy-purge loops (`202610161200:160-171`, `202610161500:64-74`), the `handle_new_user` trigger sweep on `auth.users` (`202610161200:95-110`), and the FK recreation (`pg_temp.replace_fk`, `202610161300`) depend on live catalog state.
- Whether `profiles`/`tournaments`/`tournament_registrations` (created outside migrations) carry constraints beyond what migrations added — e.g., whether `tournaments.start_date`/`end_date`/`registration_deadline`/`max_participants`/`name` are NOT NULL, or `profiles.email`/`full_name` types.
- Actual deny behavior of policies on the live DB (this audit is static); e.g., confirming `anon` truly cannot read `streams`/`team_members`/`predictions`.
- `storage.buckets` rows and other pre-existing `storage.objects` policies not written by these migrations (the migration only `drop policy if exists` its own names).
- Vault secret `feedback_server_key` existence — without it `claim_gemini_call`/`save_feedback_sentiment`/`mark_feedback_pending` always raise.
- `pg_cron` extension enabled and job `dalta-checkin-open-notifications` scheduled (the `cron.schedule` call would fail the whole migration if the extension is absent).
- `pg_trigger_depth() > 1` behavior for FK-cascade deletes on live Postgres — relied on by `check_team_member_leave`, `notify_team_member_left`, `check_prediction`, and all `log_*` triggers to exempt cascades; verified consistent in code but worth one live test (e.g., deleting an account whose team is registered for an ongoing tournament should succeed).
