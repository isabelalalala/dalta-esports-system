# Findings — F: AI sentiment pipeline (Module 5)

## Verdict

The AI sentiment pipeline is functionally correct end-to-end — every failure path degrades cleanly to "pending analysis" (`sentiment IS NULL`), the user always gets a successful submission response, validation is enforced at three layers (Gemini schema → JS → `save_feedback_sentiment`), and staff genuinely cannot see comment text. No critical defects. ~~Main gap: `analysis_attempts` has no cap~~ — **RESOLVED**: retries stop at `MAX_FEEDBACK_ANALYSIS_ATTEMPTS` (5) via `utils/feedback.ts` + the classify route; admins are exempt from the per-user claim cap and limit messages are honest about manual retry (`202610181400`).

## Findings

**Critical:** none.

**Required**

1. **No cap on `analysis_attempts`; retry never gives up.** **RESOLVED (202610181400 + classify route):** the retry query and `remaining` count now filter `analysis_attempts < MAX_FEEDBACK_ANALYSIS_ATTEMPTS` (5, shared via `utils/feedback.ts`); the admin list shows capped rows as "Gave up after N tries" and the button counts only retryable rows. Original finding: `analysis_attempts` increments on every failure (`202610181000:280`) but nothing reads it: the retry query selects *any* `sentiment IS NULL` row (`app/api/feedback/classify/route.ts:31`) and the UI only disables the button at `pendingCount===0` (`app/admin/feedback/page.tsx:163`). A permanently-unclassifiable row is retried forever — one admin click at a time — burning one app-wide claim slot per attempt. Fix: `.lt('analysis_attempts', N)` on the retry query (and a "gave up" state), or cap inside `mark_feedback_pending`.

**Nit:**

2. **Misleading pending reason when the save step fails.** **RESOLVED:** `utils/feedback-analysis.ts` now distinguishes "Gemini returned no result" (item absent from results) from "The analysis could not be saved" (result returned but the save failed). Original: marks every unsaved id `"Gemini returned no result for this comment."` — but items also land in `missing` when Gemini *did* return a result and `save_feedback_sentiment` errored or returned false (e.g. transient RPC failure). The recorded `analysis_error` blamed Gemini for a DB-side failure.
3. **`mark_feedback_pending` RPC results are never error-checked** (`utils/feedback-analysis.ts:35,76`). If that call fails, attempts/error silently stay unrecorded (row still correctly pending). Same family as the already-reported `claimError` gap at `:44` — adjacent, not identical.
4. **Admin retry is throttled by the submitter-facing per-user cap.** **RESOLVED (202610181400):** `claim_gemini_call` skips the per-user check when `get_my_role()='admin'`; app-wide 10/min and 500/day still bound retries. The "will be retried later" messages were also corrected (nothing retries automatically — the admin does). Original: the 5-per-user-per-10-min check ran against `auth.uid()` — the admin's uid on retries — so >5 retry clicks in 10 min returned "Too many sentiment requests from this account".
5. **Garbage scores silently become 0.0.** `Number(r.score) || 0` (`utils/gemini.ts:118`) maps missing/`NaN`/non-numeric scores to 0 rather than treating the item as unanswered. Harmless (score still clamped/rounded) but a malformed score is indistinguishable from a real 0.
6. **Deleted-tournament feedback is counted as "General" in reports.** `target_removed` rows have `tournament_id NULL`, so `report_sentiment` groups them in the null bucket rendered as `'General'` (`202610162300:270,278` → `SentimentSection.tsx:74,84,104`). The admin list labels them correctly ('Deleted tournament', `app/admin/feedback/page.tsx:256`); the report can't distinguish them — arguably acceptable post-deletion, flagged for awareness.
7. **`by_week` chart shows all-zero stacked bars for pending-only weeks.** `report_sentiment` emits a `by_week` row for any feedback (`:253-264`), but `sentimentSeries` only maps positive/neutral/negative (`SentimentSection.tsx:22-23`) — a week containing only pending rows renders an empty bar. Cosmetic; pending is still shown in the table column (`:84`) and banner.
8. **`analyzed` response field is dead.** `POST /api/feedback` returns `{id, analyzed}` (`route.ts:57`) but `app/feedback/page.tsx:156-163` ignores it and shows the same confirmation either way — by design per the comment, but the field is unused; could drive a subtle "analysis pending" hint.

**FYI**

- **Users cannot edit or delete their own feedback** — no user UPDATE/DELETE policies exist (`202610162200_feedback.sql:53-62`; only admin delete). Comments persist anonymously after account deletion (`user_id` → `set null`, `:12-13`). Matches the documented model ("admins delete") but is a deliberate privacy trade-off worth confirming.
- **Shared quota consumption is as designed:** one claim per submission before the Gemini call; ≥10 submissions/min pushes the rest to self-healing pending state; a single user *cannot* exhaust the 10/min cap alone (per-user 5/10 min). Two+ users at 5 each within a minute can trip the app-wide minute cap — correct conservative behavior.
- **`claimError`/missing-key/`mark_feedback_pending`-failure paths leave pending rows with `analysis_error` NULL and `attempts` unchanged** — admins see "Pending analysis" with no recorded reason; the reason is only visible live in the classify-route JSON response (`route.ts:49` → `page.tsx:95`). Partially covered by the existing claimError finding.
- **Boundary checks are consistent:** client `maxLength=1000` + trim (`feedback/page.tsx:137,153,237`), server trim+3-1000 (`route.ts:29,36`), DB `length(trim(comment)) between 3 and 1000` — exactly 3 and exactly 1000 accepted everywhere.
